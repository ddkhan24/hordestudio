# Private VH2 hosting

VH2 is not a static web page and this feature is not cloud backup. A hosted Virtual Human is a private, always-running simulation service containing its current state, memory, conversations, media, schedules, and provider configuration. Moving a life makes that service the active runtime; the local copy pauses and becomes a recovery mirror.

Horde does not sell or operate the hosting account. The owner pays the host directly and retains control of it. The service is for one owner, exposes only authenticated `/vh2/*` and `/health` routes, and does not publish the character or serve the Horde Studio interface.

## Recommended: Railway, without a terminal or domain

Use the in-app **Private server & recovery** walkthrough whenever possible. It generates the private key and shows the exact configuration block for the current Horde Studio address.

1. Create a Railway account and choose **New Project → Deploy from GitHub repo**. Select `https://github.com/ddkhan24/hordestudio` and authorize GitHub if Railway asks.
2. Open the created service, choose **Variables → Raw Editor**, and paste the four lines generated by Horde Studio. They select `deploy/vh2-self-host/Dockerfile`, let the process write to Railway's root-owned volume, install the private server key, and allow this exact copy of Studio to connect.
3. On the project canvas choose **New → Volume**, attach it to the VH2 service, and set its mount path to `/data`. Without this volume, replacing the container would erase the life.
4. Open **Settings → Networking → Generate Domain**. Use target port `8080` if Railway asks. Railway supplies the HTTPS address; no domain purchase, DNS editing, Caddy, or firewall setup is needed.
5. Wait for the deployment to turn green. Copy the complete `https://…up.railway.app` address, return to Horde Studio, and select **I have my Railway address**.
6. Paste the address and choose **Test private server**. This authenticates the service and checks browser permission; it does not upload anything. Only the final **Move running life** action transfers the life.

Railway bills the owner account. Its trial is useful for testing but is not dependable permanent storage. Free hosts commonly sleep or discard local files, which conflicts with an always-running, stateful life. Check the current price shown by Railway before deploying.

A hosted life also needs a text provider reachable from that server. Any provider that exists only on the owner’s computer becomes unavailable when the computer turns off; Horde blocks the final move until a cloud-capable provider is selected.

## Already have a managed container host

The host must support all four requirements below:

- build this repository with `deploy/vh2-self-host/Dockerfile`;
- mount persistent storage at `/data`;
- route public HTTPS to container port `8080`;
- set `HORDE_VH2_ACCESS_TOKEN` and `HORDE_VH2_ALLOWED_ORIGINS`.

The access token is a private server password, not a hosting password or AI-provider key. `HORDE_VH2_ALLOWED_ORIGINS` is the exact address from which the browser opens Horde Studio, including the scheme and port. A wildcard origin is intentionally rejected.

## Advanced: your own Linux VM

This path assumes the owner already understands SSH, DNS, a firewall, and Docker Compose. A domain is only an address; it does not install or run VH2.

“Deployment files” means the **complete Horde Studio repository**, not only the files in this directory. The Docker build copies `horde_mcp_bridge.py`, `virtual_humans/`, and `world-packs/` from the repository root. The deployment-specific files are:

- `deploy/vh2-self-host/Dockerfile`
- `deploy/vh2-self-host/compose.yaml`
- `deploy/vh2-self-host/Caddyfile`
- `deploy/vh2-self-host/.env.example`

1. Create an always-on Linux VM, install Docker and Docker Compose, allow inbound TCP ports 80 and 443, and point a domain such as `vh.example.com` to the VM's public IP.
2. Clone the complete repository on the VM and open `deploy/vh2-self-host`.
3. Generate the private key with `openssl rand -hex 32`. Copy the 64-character result and keep it private.
4. Run `cp .env.example .env`, then edit `.env`:

   ```dotenv
   VH2_DOMAIN=vh.example.com
   HORDE_VH2_ACCESS_TOKEN=paste-the-random-output-here
   HORDE_VH2_ALLOWED_ORIGINS=http://127.0.0.1:43127
   ```

   The allowed origin must exactly match the address used to open Horde Studio. It is normally not the server domain.
5. Run `docker compose up -d --build`. Caddy obtains and renews HTTPS; the `vh2-data` Docker volume stores the life under `/data`.
6. Run `curl https://vh.example.com/health`. An authorization response is expected without the token. DNS, certificate, gateway, or connection errors mean the server is not ready.
7. In Horde Studio choose **Connect my server**, paste `https://vh.example.com` and the same private key, and test before moving the life.

Never expose port 8080 directly to the internet over plain HTTP. The browser sends the bearer token with each request.

## What happens after the move

Horde pauses the local source, rejects activation while provider work is unresolved, transfers the archive directly from the browser, verifies the restored revision, configures the chosen cloud provider, and only then resumes the hosted copy. The original local life remains paused as a recovery mirror; it is not a second running life.

While Studio is open and can reach both services, confirmed server revisions are periodically saved into that mirror. **Update local recovery mirror** forces a copy. **Switch back to this computer** pauses the hosted life, saves its final revision, and promotes the mirror locally, preventing two copies from silently diverging.

If the host is genuinely unreachable, **Emergency: use local backup** promotes the last saved revision without contacting it. This is an emergency fork: the old hosted copy is marked detached and must not later run alongside the local life.

## How life storage stays bounded

VH2 no longer treats every low-level engine step as permanent human history. It uses several storage layers, each with a different job:

- **Current state:** the authoritative, complete state of each life. This includes the current relationship state and authored facts.
- **Recent engine detail:** a rolling diagnostic/replay window, normally bounded to 1,024 event rows per life. Large new event payloads are compressed losslessly.
- **Life landmarks:** a compact, immutable outline of meaningful events. Events are classified as notable, important, or tentpole; engine features may explicitly set a landmark's priority and human-readable summary. Routine clock, weather, route, and internal queue noise is not promoted into permanent history.
- **Verified checkpoint:** when the detailed ledger outgrows its window, old low-level deltas are replaced by a current-state checkpoint. VH2 replays and compares that checkpoint with the authoritative state before committing the change.
- **Exact conversation:** transcript messages remain exact and paged. They are never model-summarized by storage maintenance and disappear only through the explicit chat clear/delete controls.
- **Memory resolution:** routine experiences retain 30 days and at most 512 archive rows per life; notable experiences retain one year and at most 2,048. Important, tentpole, relationship/player-claim, creator-authored, and explicitly pinned memories remain exact permanently. Unknown future memory kinds default to notable instead of being silently discarded.
- **Other durable projections:** media and dedicated current-state records are independent of the replay ledger.

The exact transcript is the sole durable copy of conversation wording. The live
world keeps only a 32-entry window of small delivery references, so each new
reply no longer copies the entire lifetime conversation into another event.

This means “she ate dinner 100 nights ago” does not need to remain as a full engine transaction forever. A genuinely important dinner can be retained as a priority landmark, while repetitive routine details collapse into a checkpoint. Background maintenance resolves oversized ledgers one life at a time so ordinary saves and chat turns do not have to wait for the full cleanup.

New photographic assets are also bounded at import. Images larger than 2,048 pixels on their longest side are downscaled; sufficiently large opaque images are stored as optimized progressive JPEGs, and images that need transparency use WebP when available. Identical media bytes are stored once per life. This applies to **new imports only**: upgrading VH2 does not rewrite or degrade existing photos.

Photo jobs also freeze only the visual fields needed to reproduce the image,
not a second copy of the whole person and life. **Optimize service storage**
converts older oversized capture snapshots only after verifying that their
compiled image request and reference bindings remain exactly equivalent.

## Reclaiming space from an existing large database

An upgrade prevents the replay ledger from continuing to grow without resolution, but it does not automatically make an existing multi-gigabyte SQLite file small. Deleted or resolved pages may remain reusable inside SQLite instead of being returned to the host filesystem. Fresh services use incremental page reclamation so background resolution can reuse and gradually return space; the explicit optimizer remains the way to rebuild an already large legacy file immediately.

To return that unused space to disk, open the Human Workspace's storage controls and run **Optimize service storage**. The operation is deliberately explicit because it affects every life stored by that service:

1. Pause **every** life on the service.
2. Wait for chat, image, social, story, and other provider jobs to finish.
3. Close other Horde Studio windows connected to the same service.
4. Make sure the host has enough free disk for SQLite to rebuild the database safely.
5. Run **Optimize service storage** and keep the app and server running until verification completes.

Optimization replaces old low-level engine steps with a verified current-state checkpoint, applies the displayed memory-retention policy, compacts completed provider-job payloads and old photo capture context, rebuilds the SQLite file, runs an integrity check, and verifies that each life still replays to its canonical state. It preserves exact chats, relationships, authored facts, media, important and tentpole memories, creator-pinned memories, active provider work, and recovery snapshots. Removed low-level diagnostic steps, stale routine/notable memory rows, and completed-job payloads cannot be inspected afterward.

The maintenance action is service-wide, not limited to the life currently open in Studio. It also does **not** recompress existing media; old photos remain byte-for-byte unchanged. If media is a significant part of a particular service, archive or media-management policy must be handled separately rather than assuming database optimization will rewrite it.

## Operational boundaries

- Use a cloud-capable text provider. Any provider reachable only from the local computer cannot answer after that computer turns off.
- “Always on” requires a service that does not scale to zero. Sleeping free tiers delay replies and do not provide continuous wall-clock processing.
- A computer that is off cannot receive new mirror revisions. The local mirror catches up when Horde Studio is open; separately back up the cloud `vh2-data` volume for protection while the computer is offline.
- Keep additional free disk available for maintenance. SQLite may need temporary working space while rebuilding a large database, even when the final compact file is much smaller.
- Horde Studio can pause a life on the private host, but it cannot power off an arbitrary VM or cancel that provider's billing. Manage the container or VM through its owner account.
- There is no public discovery or multi-tenant sharing in this deployment. Whoever has the token has full access to every life in this container; use one private container/token per owner and rotate the token if it is exposed.
- Browser backups intentionally omit host tokens and restore as paused local copies.
